Platform Copilot

A retrieval-augmented copilot that answers operational questions about an AI/ML platform — grounded strictly in the platform's own runbooks, ADRs, and design docs, and citing its sources.

The interactive service runs a full hybrid-search + LangGraph-agent stack (OpenSearch · PostgreSQL · Redis · a served LLM) — hosting that live on Hugging Face needs a PRO Space, so this page instead shows example answers grounded in the platform's documents and cited to them, illustrating how the copilot responds. What it does

Ask an operational question; get a concise, grounded answer with sources.

Grounded + cited

Answers only from the indexed corpus and cite each source as [n]; says "I don't know" when the docs don't cover it.

Hybrid retrieval

Keyword (BM25-style) and vector (embedding) arms fused with Reciprocal Rank Fusion, so both exact terms and meaning match.

Agentic loop

A LangGraph agent guards scope, retrieves, grades relevance, rewrites and retries before answering — not a single-shot prompt.

Observable

Redis response cache, trace/cost sink, and an ingestion job scheduled with Airflow — built as a service, not a notebook.

What are the first steps when a demand-forecaster drift alert fires?

Work the DriftHigh runbook in order [1]: 1. Open the monitoring dashboard and confirm which input features breached PSI (> 0.2). 2. Check the feature-materialization job ran on schedule and did not error. 3. Compare the current input distribution against the training baseline. 4. If features are stale or wrong, fix ingestion first — do not retrain on bad data. If it is a genuine demand shift, trigger the weekly training DAG to refresh the model and confirm the new candidate clears the promotion gate before it serves traffic [2]. If the gate keeps rejecting candidates or error stays elevated, page the platform on-call and open an incident [3].

Why was Kubernetes chosen as the platform substrate instead of serverless?

So one scheduler can run every workload — CPU APIs, GPU LLM serving, batch and distributed training, and Airflow — which is what makes GPU cost control (priority classes, preemption, quotas) possible at all [1]. It also gives a declarative topology, so disaster recovery becomes "re-apply config", and it runs KServe and Ray natively [1]. Managed serverless GPU endpoints were considered and rejected: weak multi-tenant GPU economics, vendor lock-in, and no shared substrate for training + Airflow + serving — and the shared substrate is precisely the platform's value [2].

How does the platform decide whether a workload runs on CPU or GPU?

Placement is derived from the workload, not requested by the caller [1]. The platform maps a model's framework to a compute pool: GPU-bound runtimes (vLLM, Transformers) go to the GPU pool; everything else (LightGBM, sklearn/ONNX) goes to the CPU pool [1]. The GPU nodes carry a nvidia.com/gpu=present:NoSchedule taint, so only workloads that actually need a GPU — and therefore tolerate that taint — ever land there; a cheap CPU model can't silently occupy a $3/hr GPU node [2].

Why is vLLM the default LLM serving engine?

Two properties decide it [1]: PagedAttention, which nearly eliminates KV-cache fragmentation so more sequences fit per GPU, and continuous batching, which lets new requests join the running batch instead of waiting for it to drain. Together that is roughly a 5–8× throughput gain over vanilla HuggingFace generation on the same GPU. The cost model shows that throughput gain is about a 7× reduction in cost per request — so it is an economics decision, not just a latency one [2]. Vanilla HF is kept only as the benchmark baseline; TGI and TensorRT-LLM are candidate backends behind the same interface [3].

How it works

Retrieve → ground → generate → cite, behind a FastAPI service.

question │ ▼ guardrail (scope check) │ ▼ hybrid retrieve ──► keyword arm ─┐ ├─► RRF fusion ─► top-k chunks ► vector arm ─┘ │ ▼ grounded prompt (numbered context) │ ▼ LLM ──► grade → rewrite → retry (agent) │ ▼ answer + citations [n]
  • Corpus: the platform's ADRs, 7 design docs (architecture, GPU, reliability, scaling, cost, DR, security) and an incident runbook.
  • Retrieval: embeddings + keyword, fused with RRF; section-aware chunking keeps a clean heading path for every citation.
  • Generation: a system prompt that forbids ungrounded claims; citations are attached from the retrieved chunks, so sources are always accurate.
  • Interfaces: FastAPI /search + /ask, a Gradio chat UI, and a Telegram bot — all sharing one tested render path.
